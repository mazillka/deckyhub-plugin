# DeckyHub agent guide

This file provides guidance to coding agents (including Claude Code) working in this repository.

## What this is

DeckyHub is a [Decky Loader](https://decky.xyz/) plugin for Steam Deck: a Python backend (`main.py`) driving a React/TypeScript frontend (`src/`), packaged so Decky Loader can load it in Gaming Mode. It discovers, downloads, and updates other Decky plugins/tools from tracked GitHub repositories. It never installs or executes anything without an explicit tap: besides downloading ZIPs, it offers an optional **Install** / **Update** / **Uninstall** in a Decky plugin's Manage window (Uninstall behind a confirmation, since Decky Loader deletes without one; Install/Update for a release not yet installed, or newer than installed) and a one-tap self-update, both via Decky Loader's own installer — see the self-update note under Architecture.

## Commands

```bash
corepack enable
pnpm install
pnpm run typecheck        # tsc --noEmit
pnpm run build             # rollup -c -> dist/index.js
pnpm run test:backend      # python -m unittest discover -s tests
pnpm run test:frontend     # node --test tests/version.test.ts
npm run test:e2e --prefix devtools/decky-mock
```

Run a single backend test: `python -m unittest tests.test_plugin_status.PluginStatusTests.test_decky_plugin_detection_reads_manifest_and_package_version`. The backend uses only the Python standard library — no pip install needed.

`test:frontend` unit-tests the pure version logic in `src/version.ts` with Node's built-in runner (Node 24 strips the types), so keep that file free of imports. The Playwright suite in `devtools/decky-mock/` covers the browser UI; `pnpm run typecheck` remains the static correctness gate for `src/`. Run `npx playwright install chromium` once before its first local run.

## Development rules

- Keep the backend dependency-free; it uses only the Python standard library.
- Branch all new work from `develop` and open PRs against `develop`; `main` is for stable releases only. Never work directly on either; branch naming and the pre-commit guard are in [CONTRIBUTING.md](CONTRIBUTING.md#releases).
- Any new `@decky/ui` import used in `src/` needs a matching stand-in added to `devtools/decky-mock/ui.tsx`, or the mock's build fails with "No matching export in ui.tsx".
- Download progress and install instructions are one shared modal (`showDownloadModal()` in `src/components/DownloadProgress.tsx`), used by every download-to-`/home/deck/Downloads`-style entry point (Updates/Discover, DeckyHub's "Download ZIP" fallback in `DeckyHubUpdateModal.tsx`, and the dev-mock preview buttons). Don't hand-roll a separate copy for previews or a new call site — it silently drifts from the real component (this happened once already). Install / Update / Downgrade buttons (every `installDeckyPlugin()`/`updateDeckyPlugins()` call) reuse the same modal via `showInstallDownloadModal()`, which polls `stage_install`'s frontend-chosen job id, then spins ("Preparing install…") until Decky Loader's `install_plugin` call returns (its own dialog is up) and closes.
- A component rendered via `showModal()` cannot call `useT()` (or read any other React context) — `showModal()` mounts onto a separate root from the caller's tree (Decky's own MAIN-window modal manager in production; a fresh React root in the local mock), so `I18nProvider` never reaches it. Resolve `t` in the component that still has context and pass it down as a prop (see `DownloadProgress.tsx`'s `DownloadModal`, `DeckyHubUpdateModal.tsx`) — calling `useT()` inside a modal component throws `"useT must be used within I18nProvider"` the instant it mounts.
- Preserve Steam Deck controller navigation: custom layouts need `Focusable` with valid `flow-children` values. Test controller behavior on real hardware before release; the browser mock cannot validate it.
- `docs/` is the GitHub Pages site (promo `index.html`, `404.html`; the registry editor and catalog page live in mazillka/deckyhub-registry's `docs/`), assembled by `devtools/build-site.py` in `.github/workflows/pages.yml`: it downloads mazillka/deckyhub-registry's `apps.json`, renders the catalog into `index.html` and generates the WebP screenshots, so adding a registry app or replacing a screenshot needs no page edit. The workflow also runs daily to pick up registry changes.
- Treat registry data as trusted project data, but keep download URLs HTTPS and filenames reduced to a basename.

### Local browser preview (no Steam Deck needed)

`devtools/decky-mock/` swaps `@decky/ui`/`@decky/api` for plain `<div>`/`<button>` stand-ins (`devtools/decky-mock/ui.tsx`, `api.ts`) and bridges backend calls to the real, running `main.py`. Two processes, both from that folder: `python dev-server.py` (backend bridge on :8642) and `npm run dev` (frontend on :5183, first run needs `npm install`). This is for exercising layout and logic only — real `@decky/ui` components are scraped at runtime from Steam's own webpack bundle (`findModuleExport()`), so nothing here is pixel-accurate. Always do a final visual/gamepad check on real hardware before shipping a UI change — this mock can't validate Steam's focus/gamepad-nav system at all.

`DevShell.tsx`'s "Preview" nav has standalone buttons (alongside the real routes) to open the download-progress and download-complete modals directly via the real `showDownloadModal()`, without triggering an actual download — `dev-server.py` seeds a fixed, never-completing `"preview-job"` entry in `plugin.downloads` at startup so the modal's real polling has a stable state to render instead of erroring on an unknown job id.

## Release

Release steps (version bump, `v*` tag, and the back-merge of `main` into `develop` with a merge commit after each stable release) are in [CONTRIBUTING.md](CONTRIBUTING.md#releases). The tag triggers `.github/workflows/release.yml`. Its `build` job (read-only token) checks the tag matches `package.json`'s version, installs, typechecks, builds, runs the frontend, backend and browser E2E tests, and zips `plugin.json` + `main.py` + `dist/index.js` (no source map) + `package.json` + `LICENSE.md`, and hands `DeckyHub-vX.Y.Z.zip` to the `publish` job, the only one with `contents: write`, which attaches it to a GitHub release.

**Every release (pre-releases too) gets human-friendly release notes.** The workflow's `--generate-notes` only lists raw commit/PR titles, so once the release exists, replace its body with `gh release edit vX.Y.Z --notes-file <file>`:

- Cover everything since the previous release tag (`git log --no-merges <previous-tag>..vX.Y.Z`), described as it ends up, not step by step — a feature renamed or moved twice is one line in its final form.
- Group under **New**, **Changed** and **Fixed** (omit empty groups); plain language a Steam Deck user understands — what they'll see or can now do, not function names, commit hashes or version-bump commits.
- Keep internal-only work (refactors, tests, tooling) to an optional short **Under the hood** list.
- End with a short **Try it on your Deck** list of what to check on real hardware when the release touches UI, controller navigation or installing.

## Architecture

**Backend (`main.py`) is one `Plugin` class** exposing async methods Decky calls directly from the frontend via `callable()` (see `src/api.ts` for the full RPC surface — `get_apps`, `download_asset`, `save_settings`, etc.). There's no HTTP API of its own.

- **App identity vs. live state**: an "app" entry (registry or custom) is static metadata — `repo`, `category`, `detect` rule, `asset` include/exclude filters. `get_apps` merges that with `installedVersion` (computed by scanning `$DECKY_HOME/plugins/*/plugin.json`; `decky-plugin` is the only `detect` type) but leaves `latestVersion`/`assets`/`updateAvailable` null — the frontend fetches those itself.
- **Registry** starts from the `registry-cache.json` copy in the settings dir (else nothing: no list ships in the ZIP) so startup never waits on the network, then refreshes in the background from [mazillka/deckyhub-registry](https://github.com/mazillka/deckyhub-registry) (`main` branch `registry/apps.json` on `raw.githubusercontent.com`) via `fetch_remote_registry()` in `main.py`, then emits `registry_updated`, which `src/index.tsx` forwards as the window `REGISTRY_UPDATED` event so open pages reload. An empty official download is treated as a failure, so a broken publish can't overwrite the last good cache. `parse_registry()` drops malformed entries (wrong types, or a `repo` that isn't a strict `owner/name` - `REPOSITORY_NAME` (`main.py`) rejects dot-only parts, since the frontend builds GitHub API paths from it). A user-added entry that reuses an earlier source's `repo`, `id` or detect name is skipped. Custom (user-added) repos are synthesized on the fly in `_custom_apps()` and merged in per-call — they're never written into the registry file.
- **The curated list lives in its own repository**, [mazillka/deckyhub-registry](https://github.com/mazillka/deckyhub-registry), whose CI runs `tests/test_registry_schema.py` from this repo against its file (`DECKYHUB_REGISTRY`; the test skips without it). This repo no longer keeps a copy: releases from before the move, which read `registry/apps.json` from this repo's `main`, keep their cached or bundled list.
- **Users can add their own registries** from **Repositories** → **Custom Registries**. That page has one field: an `owner/repo` is expanded via `registryUrlForRepo()` (`src/utils.ts`) to the same `raw.githubusercontent.com/.../registry/apps.json` shape, and anything else is sent as a URL. The page sends the resolved URL; the backend only stores and validates it (`validate_registry_url()` — HTTPS, `.json` path, length cap) and caps the list at `MAX_CUSTOM_REGISTRIES`. `_load_registry()` loads the official source first, then each added one, **first source wins** on `repo`, `id` and `detect.names` (with `DeckyHub` reserved) so an added registry can never override an official entry's detect rules or asset filters, nor claim an installed plugin's name and offer an Update that installs its own repo's release over it. Each source caches independently (`registries/<sha256[:16]>.json`, hashed from the URL so two lists can't clobber each other) and a source with neither a live copy nor a cache is skipped rather than failing the load. `add_custom_registry()` fetches once before saving, so a dead URL fails in the UI instead of being silently dropped at every startup, and refuses (`nothing-new`) a list whose every entry is already shown; the decky-mock bridge serves fixture registries from `https://registry.test/` so E2E can exercise this without the network; add/remove reload `self.apps` from caches (no extra downloads; remove also deletes that source's cache), `refresh_registry()` re-downloads every source, and the page dispatches `REGISTRY_UPDATED`.
- **All HTTPS goes through `verifying_ssl_context()` in `main.py`**, wired into the shared `_OPENER` (alongside its HTTPS-only redirect handler), never a bare `urlopen`. Decky Loader runs plugins under a PyInstaller-bundled Python whose OpenSSL was compiled against Debian's certificate layout and looks under `/usr/lib/ssl` — a path that does not exist on SteamOS, which is Arch-based and keeps its CAs in `/etc/ssl`. The result is a default context that trusts *nobody*, so every fetch fails with `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`, the official registry silently falls back to its cache (or an empty list), and only explicit actions like adding a registry surface an error. `verifying_ssl_context()` builds the normal verifying context and, **only when it comes up with zero certificates**, loads a CA bundle from `CA_BUNDLE_PATHS`. Verification stays on: a self-signed, expired or hostname-mismatched certificate still fails exactly as before.
- **Downloads are queued, not fire-and-forget**: `download_asset` pushes onto `self.download_queue`, drained one at a time by `_run_download_queue()` → `_download()`. Progress/state lives in `self.downloads[job_id]`, polled by the frontend via `get_download`. Cancellation is cooperative: `cancel_download` adds an active (queued or downloading) job_id to `self.cancelled`, and `_download` checks that set before it starts and while it runs; `clear_downloads` skips the files of active jobs. `_download` tries `urllib` first, falls back to system `curl` on `URLError` (some CDNs 403 Python's default UA/TLS stack); both refuse redirects off HTTPS. SHA-256 verification is opt-out for normal downloads, mandatory for DeckyHub self-updates.
- **Version comparison** happens entirely client-side in `src/version.ts` (`compareVersions`, used by both `hydrate` and `resolveDeckyHubInstallType` in `src/utils.ts`) — the backend never decides "update available"; it just supplies `installedVersion`, and the frontend fetches `latestVersion`/`publishedAt` directly from the GitHub API and compares the dotted version number plus any pre-release suffix, piece by piece (`1.0.3-alpha.5` < `1.0.3-beta.1` < `1.0.3-rc.2` < `1.0.3-rc.10` < `1.0.3`).

**Frontend (`src/`) talks to GitHub directly from the browser**, not through the Python backend — every release lookup (`hydrate()`, `listAppReleases()`, `listDeckyHubReleases()`, `latestDeckyHubRelease()` in `src/utils.ts`) goes through one `fetchReleases(repo)`. It first looks the repo up in the registry's release index: `releases.json` on mazillka/deckyhub-registry's `release-index` branch, which that repo's `release-index` workflow rebuilds every 30 minutes from `scripts/build_release_index.py`. It's read once via `fetchReleaseIndex()` (built on `cachedRawJson()`, which shares one download of a raw registry file among all callers) from raw.githubusercontent.com (outside the API rate limit, header-less so no CORS preflight), re-read on a forced refresh at most once a minute, and ignored when over 6 hours old. The same job writes `stats.json` beside it: per repo, all-time downloads, GitHub stars, the shown release's date and whether its `plugin.json` asks for root. `fetchPluginStats()` reads it (also via `cachedRawJson()`) for Discover only; `Content.tsx` puts each repo's line on `App.stats`, which drives the card's and Manage window's `AppStats`/`AppBadges` (`src/components/AppCard.tsx`), the Downloads/Stars/Updated sorts and the total-downloads badge. A missing file just leaves them out. Repos it lacks (self-added repos, custom registries) fall back to `fetchNoCors` from `@decky/api` against `api.github.com`. This means release/version data is rate-limited by GitHub per-device — 60 req/hr (10/min search) unauthenticated, 5,000/hr (30/min search) once a user sets a personal access token in Settings. A 403/429 there is virtually always that limit, not a real access error, so `githubResponseError()` turns it into a message naming the rate limit and, when the response's `retry-after`/`x-ratelimit-reset` headers say so, roughly how long to wait (plus a hint to add a token, if none is set), instead of a bare status code — and, when no token is set, also calls `reportRateLimit()`, which raises `RateLimitBanner` (a dismissible notice with a link to Settings) at the top of every screen that calls GitHub until the limit resets or a token is saved. `fetchReleases()` caches each repo's raw release list in `localStorage` (`readCache`/`writeCache`, `CACHE_TTL` = 30 minutes, keyed per repo) and callers apply their own channel/tag/asset filters on top, so the cards and both version pickers share one fetch; the cache is bypassed with `force=true` — wired to every explicit "Refresh"/"Check for Updates" action, never to the automatic loads that happen on mount, channel switch or the 15-minute background refresh. Unauthenticated GitHub calls send **no request headers at all** (no `Accept`, no `If-None-Match`/ETag re-check): any header turns `fetchNoCors` into a CORS preflight to Decky Loader, and on a real Deck (Decky 3.2.10) those preflights were seen to stall indefinitely once Chrome's 6-socket pool for them filled with ones the loader never read, hanging every GitHub call for its full 15 s timeout while header-less requests still worked; with a token set the `Authorization` header makes the preflight unavoidable. If a fetch fails and an older entry exists, that entry is returned instead of an error (the rate-limit banner still shows). An empty release list is treated with suspicion too: GitHub sometimes answers `[]` to an authenticated request for a repo that has releases, so with a token set `requestReleases()` asks once more without it, and an empty answer never replaces a cached non-empty list. GitHub's `GET .../releases` list endpoint has been observed **not** reliably sorted newest-first (a just-published release returned mid-array instead of at index 0), so `fetchReleases()` sorts by `published_at` itself rather than trusting response order for "latest". "Latest" for a channel is the newest matching release among the last 20: the stable channel sees only stable releases, the pre-release channel sees every release (`inChannel()` in `src/version.ts`), so a stable release newer than the last pre-release still reaches people on pre-releases.
- **GitHub token**: stored server-side as `settings.githubToken` (validated/trimmed by `_coerce_settings()` in `main.py`; the backend itself never uses it — its own network calls hit `raw.githubusercontent.com` and release-asset CDN URLs, a different, effectively unlimited bucket). On the frontend it lives in a module-level variable in `utils.ts` (`setGithubToken()`/`githubHeaders()`), not React state, since it's read from plain async functions outside any component tree. Every route mounts its own `I18nProvider` (see below), and that provider's settings-loading effect is also what primes the token on mount and re-primes it whenever `SettingsPage` saves a new one (via the same `LOCALE_CHANGED` event used for locale changes) — so there's no dedicated "token changed" event of its own. Because React runs a child's effects before its parent's, a route's first GitHub call can fire before that provider has loaded the token, so every api.github.com call goes through `githubFetch()`, which waits once for the saved token (`getSettings()`) before its first request.

- **`Content.tsx`** is the shared list view for both the Updates and Discover routes (`fullPage` prop selects which), including the app grid and search/status filters. **`AppCard.tsx`** renders one app's status/version and its download buttons. **`DownloadProgress.tsx`**'s `showDownloadModal()` is the single download UI used by `Content.tsx`, `DeckyHubUpdateModal.tsx`, and the dev-mock preview: it opens a modal that self-polls `get_download`, shows progress with a Cancel button while active, and swaps in place to install instructions (or an error) once the job settles — callers just disable their download buttons via an `onSettled` callback. **`SearchPage.tsx`** (`/deckyhub/search`, titled **Search & Install**) searches GitHub, keeps only repos with a root `plugin.json` (read from raw.githubusercontent.com) or already listed, and offers **Install** (adds the repo via `add_custom_repo`, then the same `startPluginInstall()` a card uses) and **Add**. **`ManageRepositoriesPage.tsx`** and **`SettingsPage.tsx`** are separate routes too; all are registered in `src/index.tsx` via `routerHook.addRoute`.
- **Custom-events-as-pub/sub**: cross-component signals (`REGISTRY_UPDATED` in `api.ts`, `LOCALE_CHANGED` in `i18n/index.tsx`) are plain `window.dispatchEvent`/`addEventListener` `CustomEvent`s, not React context — grep for these constants before assuming a settings change needs prop drilling.
- **i18n** (`src/i18n/`) is a from-scratch key/template system, not a library: `en.ts` is the canonical `MessageKey` type every other locale file must satisfy, `useT()` looks up the current locale's string (falling back to English) and does `{var}` substitution. Plain functions in `utils.ts` that build user-facing text with no component tree (GitHub errors, the updates toast) use `tr`, which `I18nProvider` points at the current locale via `setTranslator()` — don't hard-code English there.
- **Gamepad/controller navigation** on Steam Deck depends on wrapping any custom-layout container (e.g. a CSS grid) in `<Focusable>` from `@decky/ui` with the correct `flow-children` value — these are literal Panorama/SteamUI focus-flow keywords (`"right-wrap"` for a wrapping left-to-right grid, etc.), not arbitrary strings; an unrecognized value silently falls back to plain vertical flow with no error. `PanelSection`/`ButtonItem`/`PanelSectionRow` handle focus automatically; a raw `<div>` does not.
- **DeckyHub's own self-update is split across two components**, mirroring the pattern in unifideck (a similarly-shaped Decky plugin): `DeckyHubUpdate.tsx` is deliberately thin — just a `PanelSection` titled `"DeckyHub vX.Y.Z"`, laid out like an app card: a note naming the newer release and an **Update** button once one is known (its accessible name stays `"Update to vX.Y.Z"`; the full label doesn't fit beside the gear in Quick Access) (it hands that release straight to `installDeckyPlugin()`, hidden by Display Settings' "Update" like the cards' button) and **Manage**, which opens `DeckyHubUpdateModal.tsx` via `showModal()`. The modal owns everything else: a stable/pre-release channel `DropdownItem`, a version `DropdownItem` listing recent releases for that channel (fetched via `listDeckyHubReleases()` in `src/utils.ts`, which hits `GET /releases?per_page=20` — the same cached list `latestDeckyHubRelease()` picks the panel's background check-and-toast release from), and the install actions for whichever release is selected. The primary button's label/action (`resolveDeckyHubInstallType()` in `utils.ts`) is one of **Update to vX** / **Reinstall vX** / **Downgrade to vX** depending on how the selected version numerically compares to the installed one — reinstalling or downgrading are first-class, not hidden.
- **The primary button hands the install to Decky Loader, not this plugin's backend.** `@decky/api`'s `call`/`callable` are scoped to this plugin's own RPC connection and cannot reach Decky Loader's global routes, so `getDeckyBackend()` (in `utils.ts`) goes through `window.DeckyBackend` (falling back to `window.opener?.DeckyBackend` for the Quick Access Menu's popup window in Gaming Mode) and calls the loader-global `utilities/install_plugin` route directly (via `installDeckyPlugin()`, shared with the Manage window's **Install** / **Update**, which uses the `pluginName` `get_apps` reports for decky-plugin detections) — the same one the Decky Store's own install button uses. That route pops Decky's own native confirm/progress dialog and does the verify+install itself, so the modal closes as soon as it hands the release over. The download is the one step DeckyHub keeps: `installDeckyPlugin()`/`updateDeckyPlugins()` first call `stage_install` (`main.py`), which downloads the ZIP with DeckyHub's own downloader into `$DECKY_PLUGIN_RUNTIME_DIR/installs/` (same release-asset check and SHA-256 verification as `download_asset`), and hand Decky a `file://` path with the same hash. Decky Loader 3.3.0's own fetch of a GitHub release URL was seen to hang for good on a real Deck (no socket, no timeout), while a `file://` artifact is read straight from disk. Staging happens before a fresh-install plugin's uninstall, so a failed download leaves it installed; files older than a day are swept on the next stage, since Decky reads one only once its dialog is accepted. The decky-mock bridge replaces `stage_install` with a no-network stand-in, so E2E sees `file:///deckyhub-installs/<asset name>`. Once the install finishes Decky reloads DeckyHub's backend and frontend itself (`import_plugin` → `loader/import_plugin`); as a fallback, `reloadIfStillOld()` in `utils.ts` waits Decky's 15 s load timeout and, if the old copy was never dismounted (`markUnloaded()` in `onDismount`), calls `window.DeckyPluginLoader.importPlugin("DeckyHub")`. Both version windows (this one and a plugin's Manage window) close on every action except **Check for Updates** and **Download ZIP**, which keeps the window open beneath the shared download-progress window. The **"Download ZIP"** button next to it is the older, always-available fallback for the selected release, going through the same `download_asset`/download-queue path as every other download and the shared `showDownloadModal()`.

## Security boundaries

The full policy is in [CONTRIBUTING.md](CONTRIBUTING.md#security-boundaries). Implementation points: `download_asset` (and `stage_install`, through the same `_validate_download_asset`) raises on non-HTTPS URLs and reduces filenames to a basename (path traversal guard), and `import_custom_repos` restricts the source file to a `.json` under `/home/deck`. Never disable certificate verification to work around a trust-store problem — `verifying_ssl_context()` fixes *where* the roots are read from while leaving `CERT_REQUIRED` and hostname checking on; a registry that can't be verified must fail, not be fetched anyway. A user-added registry is fetched only over HTTPS (enforced by `validate_registry_url()`, and `fetch_remote_registry()` rejects a redirect off HTTPS), the response is capped at `MAX_REMOTE_REGISTRY_BYTES`, and its entries only ever name GitHub release assets of the repo they declare — the same `download_asset` check applies, so an added registry can't widen what the plugin is willing to download.
